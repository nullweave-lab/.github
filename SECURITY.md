# Security policy

## Reporting a vulnerability

Do **not** disclose suspected vulnerabilities, exploitation chains, sensitive bypasses, credentials, or production details in a public issue, discussion, pull request, commit, or test fixture.

Use GitHub's private vulnerability reporting or a private security advisory for the affected repository when that option is available. Include:

- affected repository and revision;
- affected component and configuration;
- impact and attacker prerequisites;
- minimal reproduction information;
- whether the issue is already public;
- suggested disclosure constraints.

If private reporting is unavailable, open a public issue containing only a request for a private reporting channel. Do not include technical details in that issue.

## Scope

Security reports are relevant when they affect public PARC specifications, reference implementations, parsers, proof generation, signature or freshness validation, test tooling, or disclosure controls.

Production services, private policy engines, confidential rule packs, infrastructure, and patent material are not maintained in the public repositories and must not be attached to public reports.

## Disclosure process

We aim to validate reports, determine affected versions, coordinate remediation, and publish a proportionate advisory after a fix or mitigation is available. Timelines depend on impact, reproducibility, cross-repository dependencies, and the risk of enabling active exploitation.

No repository in this organization should be interpreted as offering a guarantee of absolute security or universal resistance to bypass.
